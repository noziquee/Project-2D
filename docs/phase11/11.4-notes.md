# Phase 11.4 – Weapon switching input

Run in Godot 4.7.2 (headless): the full run is `SUMMARY passes=669 failures=0` (see 11.2 notes). This step's share is **18 checks** (section YY: YY1 to YY15 with YY7pre, YY8b and YY13pre).

## What changed
- `project.godot`: new input action `weapon_next`, bound to **Q**. Change it in Project Settings > Input Map.
- `WeaponController2D.gd`: new export `loadout: Array[WeaponDefinition2D]` and `equip_next() -> bool`. It equips the next weapon of the loadout after the one equipped now, wrapping around. It does nothing (false) when the controller is not initialized, the loadout is empty, or the character is in a swing or charge. A weapon that cannot be equipped is skipped: `equip()` has already rolled back and logged its problems, and the next entry is tried. False when none could be equipped.
- `player.gd`: in `_sample_attack_input()`, a press of `weapon_next` calls `weapon_controller.equip_next()` before the attack ids are read, so that frame already uses the new weapon. A dead player never gets there.
- `player.tscn`: the `WeaponController2D` node has `loadout = [sword, bow]` (two new ext_resources). `starting_weapon` is still the sword.
- `tests/smoke_checks.gd`: section YY.

## Decisions
- **The loadout lives on the weapon controller, not in `player.gd`**, so any character with a controller can switch, and tests can set it without input.
- **The loadout should include `starting_weapon`.** If the equipped weapon is not in the list, the cycle starts at the first entry.
- **A press during a swing or charge is dropped**, not buffered (the same rule as the return clip in 9.R2). `equip()` itself still refuses during a swing; `equip_next()` just checks first so it is silent.
- **A hold in progress carries over.** The attack ids are read each frame from the equipped weapon, so a light press that began with one weapon ends as the light attack of the other. This is a corner case; check it in V3 if it feels wrong.
