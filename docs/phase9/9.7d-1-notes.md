## What changed
- `player.gd`
  - New `get_light_attack_id()`: the `light_attack_id` override, else the component's default attack (the weapon's first combo attack).
  - New `get_heavy_attack_id()`: the `heavy_attack_id` override, else the equipped weapon's `heavy_attack.id`, else empty (no controller, or a weapon with no heavy).
  - `heavy_attack_id` now defaults to **empty** (it was `player_heavy`). Both exports are optional overrides.
  - `_sample_attack_input()` uses the two getters. A weapon with no heavy attack behaves like before "no heavy registered": `attack_light` fires the light attack on press and `attack_heavy` does nothing.
- `tests/smoke_checks.gd`: section OO appended. Changed on purpose: **U3** (exports are empty, the heavy id comes from the sword), **Z1** and **Z5b** and **GG1** (they read `get_heavy_attack_id()` instead of the export).
- `docs/phase9/PLAN.md`, this note.

## Tests (section OO, 12 checks)
OO1 the shipped player has empty overrides and gets `player_light` / `player_heavy` from the sword; OO2 each override wins when set; OO3 a code-built weapon with its own light and heavy is equipped, the hold charges its heavy and the release swings it; OO4 a weapon with no heavy leaves the heavy id empty and `attack_light` swings on press; OO5 equipping the sword again restores both ids; OO6 with no controller the heavy id is empty and the light id is still the default attack.

## Look in play
Nothing should change: tap = light, tap again inside the window = light 2, hold = heavy charge, release = swing.
