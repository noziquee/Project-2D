# H9.4: single target marker and interruptible auto-approach (plan)

Written October 28, 2026. Nothing here is built yet. Read from the project as it stands after H9.3 (suite on a copy: `passes=1569 failures=0`, not yet run on your machine).
Put this file at `docs/trackH/H9.4-plan.md`. Fixes target T4 of `H9-scene-and-combat-rework-plan.md` and changes D20.

**Rule that runs through it (same as H9):** code owns the rules (who is targeted, range, cancel, cooldown, cost). Scenes own the look. The approach adds no second movement controller: `MovementComponent2D` stays the only thing that applies velocity.

## 0. Correction first: only one target is marked

**Problem.** After H9.3 every eligible enemy on screen gets a ring: the selected one a strong ring, all the others a light one (`_update_assist_indicator()` builds `others` from `candidates_in_shape()`, and `show_other_targets` defaults to true). You do not want that.

**Decision D23 (supersedes the "light marker" half of D20):** exactly one marker is ever shown, on the target the next light tap would hit. There is no light ring for other targets. `show_other_targets`, the `others` argument of `AssistIndicator2D.show_state()` and the `other_marker_*` exports go away.

**Decision D24 (selection rule, my reading of "facing direction / nearest"; please confirm):**
1. Look at the targets inside the camera view (unchanged, T1).
2. Those inside a front cone round the aim axis win over any outside it. The axis is what the code already uses: the player's aim (mouse, stick, drag), else the last aim, else the facing.
3. Among the winners the nearest to the player is chosen. If nothing is in the cone, the nearest target on screen is chosen.
4. The current target is kept while it stays valid and in view (the existing sticky bonus), so the marker does not flicker between two enemies at similar distances.
The cone is an export, `front_angle`, default 120 degrees (60 each side of the axis).

### Steps (H9.4.0)
- `player.gd` `_update_assist_indicator()`: stop collecting `others`; call `show_state(radius, target)`. Remove `show_other_targets`.
- `AssistIndicator2D.gd` / `.tscn`: remove `get_other_targets()`, the light-ring drawing and its three exports.
- `ViewAimShape2D.gd`: add `front_angle`; override the scoring so any target inside the cone scores above any target outside it, and within each group nearer is better. Keep `keeps_target()` as is.
- Checks to change: H9-31 (now: with several enemies in view exactly one marker is drawn), H9-32 (drop, it is covered), H9-33 (drop, the switch is gone), H9-45 (nearer one on the aim still wins; keep, re-check with the new scoring), H9-47 to H9-49 (re-run; the kept-target rule must still pass).
- New checks (H9-50 onward): five enemies on screen, one ring; a farther enemy in front beats a nearer one behind; nothing in front, the nearest wins; the marker's target is the one the swing turns toward (marker and swing agree); the marker survives two enemies swapping nearest by a few pixels.
- Run the suite. This step is small and fixes the visible bug, so it ships alone.

## 1. What already exists (audit result, so H9.4 reuses it)

| Need | Where it already is |
|---|---|
| Move the character | `Character2D._physics_process` sets `context.movement_input = _get_movement_input().normalized()` at the top of every frame; `MovementComponent2D` turns it into velocity. The approach only has to supply a direction through `_get_movement_input()`. |
| Face the right way | `FacingComponent2D.update()` faces the last horizontal movement direction, and during an attack the side the attack points to (with a dead zone and sticky facing). Walking toward the target therefore already faces the movement direction, and the swing already faces the target (the attack direction is the direction to the target). Nothing new is needed here beyond tests. |
| Pick the target | `TargetingService2D.resolve()` / `pick_target()` / `get_action_target()`, `is_eligible()`, `keeps_target()` on the view shape (the target stays valid while in view). |
| How far an action reaches | `AttackDefinition2D.get_reach()` and `SkillDefinition2D.get_reach()` (H9.1c, nothing reads them yet). This is the number the approach closes to. |
| Where the request is consumed | Light tap: `_sample_attack_input()` sets `_pending_light`, then `Character2D` calls `try_start_attack(id, _get_attack_direction())`. Heavy: `_pending_begin` / `_pending_release`. Skills: `skill_component.try_use_slot()` inside `_sample_attack_input()`. |
| Costs and cooldowns | `SkillComponent2D.try_use_skill()` checks `can_use()`, then pays mana and starts the cooldown at the moment it casts. `AttackComponent2D` gates on cooldown, an attack in progress, dash and hit stun. Because both only act when the action actually starts, an approach that casts only once in range costs nothing while walking. |
| Movement slowed by an attack | `context.move_multiplier` (the attack's `movement_multiplier`). Untouched. |

**Gaps found:**
- There is no "is this target inside this reach, counting its size" helper. The AI has its own range logic; the player has none.
- `get_reach()` is measured from the character's origin, the same point the blue circle is drawn from. The check uses that point too, so the circle, the in-range test and the swing agree.
- A target's size is only approximated today (`target_margin`, 8 px). H9.4.1 decides whether that is enough or whether to read the target's hurtbox extent.
- A heavy attack commits on button release, after the charge. See D25.
- A skill's cost is paid inside `try_use_skill()`, so the range check must come before it.

## 2. The behaviour (what you asked for, as rules)

1. An attack input (light tap, heavy release, aimed skill) with a target selected:
   - in range: face the target and attack, exactly as today;
   - out of range: walk toward the target, facing the movement direction; attack the moment the target is in range.
2. Range and target validity are checked again at the moment of attack, not when the button was pressed. The reach comes from the attack that is equipped at that moment.
3. Any manual movement input (stick, keys) cancels the approach at once. It does not resume until the next attack input.
4. No approach when there is no target (the tap swings toward the aim as today), when the aim is manual (a drag or a pushed right stick is a deliberate direction), or for actions with reach 0 (self buffs).
5. Dash, hit stun, death, the target dying, the target leaving the view, or a weapon swap that removes the attack also end the approach.
6. Safety limits so the player never chases forever: a maximum approach time (export `max_approach_time`, default 3 s) and a stall check (cancel if the distance has not shrunk for 0.5 s, for example against a wall).
7. A visible target out of range stays targeted and marked. Visibility never grants range.

## 3. Build order (each step is its own zip and ends with a suite run)

**H9.4.0 Single marker.** Section 0. Ships first.

**H9.4.1 Range helper (no behaviour change).**
- Add `TargetingService2D.is_in_reach(origin, target, reach)` (or a small static helper beside it): distance to the target minus its size allowance is at most `reach`.
- Decide the size allowance: start with `target_margin`; if the goblin and a large object differ visibly, read the hurtbox shape's extent instead. Record the choice.
- Checks: in range, just outside, exactly on the edge, a large target, `reach` 0.

**H9.4.2 The approach as plain data and decisions (no input wiring).**
- New `AutoApproach2D` (a small `RefCounted` in `Characters/Components/Aim/`): holds the kind (light, heavy, skill), the id or slot, the target, the elapsed time and the stall timer. It answers `direction(origin)`, `in_reach()`, `should_cancel(...)`. It moves nothing.
- Exports for `max_approach_time` and the stall limit live on the player.
- Checks with stand-ins: starts, steps toward, ends in range, ends on timeout, ends on stall, ends when the target is freed or leaves the view.

**H9.4.3 Light attack (the whole loop, light only).**
- `player.gd`: when `_pending_light` is set and the attack could start now, resolve the target (same call the marker uses). No target or in reach: unchanged. Out of reach: clear `_pending_light` and start an approach.
- `_get_movement_input()`: manual input first (and a manual input cancels the approach); otherwise the approach direction. Dash cancels it.
- Each frame while approaching: re-validate the target, re-read the equipped light attack's reach, and when in reach put the id back into `_pending_light` so the normal path starts the swing that same frame.
- Checks (H9-5x onward): approach starts out of range; swings once in range and faces the target; manual input cancels at once and does not resume; the next tap starts a new approach; target dies mid-approach; target leaves the view; weapon swap changes the reach (bow versus sword) or removes the attack; cooldown on the light attack is respected; hit stun and dash cancel; a drag aim never approaches; max time and stall.
- This is the first step you can play. Expect to tune only the cone and the two limits.

**H9.4.4 Heavy attacks.** Needs your decision D25, below, then an audit of `begin_charge` / `release_charge` / `_commit_release`.
- Checks: out-of-range release, charge ratio kept, cancel, cost and cooldown.

**H9.4.5 Skills.**
- Aimed skills with a target and `get_reach()` above 0: if `can_use()` refuses (cooldown, mana), refuse exactly as today and do not approach; otherwise approach and cast in reach. Self skills, buffs and placed ground circles with no target keep their current behaviour.
- A dash skill already closes distance itself: it approaches only when the target is beyond `max_range` plus strike radius (that is what `get_reach()` returns for DASH).
- Checks: mana and cooldown are not spent while walking, spent once at the cast; refused skill does not move the player; every skill type with a reach.

**H9.4.6 Feedback (optional, small).**
- The marker can show "locked, approaching" (a second colour or a pulse) through an `@export` on `AssistIndicator2D`, a replaceable placeholder in the H9.6 sense. Gameplay never reads it.

**H9.4.7 Regression and notes.**
- Suite after every step. By hand: sword light tap at a far enemy, same with the bow, weapon switch while walking, stick interrupt, dash interrupt, an enemy leaving the screen, two enemies close together (marker stable).
- Write `docs/trackH/H9.4-notes.md` and update `docs/STATUS.md` (D23 to D25, the new counts, a note that H9.3's "a tap at a far target misses" is resolved for light attacks after H9.4.3).

## 5. Risks

- The suite has never been run on your machine since H9.1. H9.4.0 changes the H9.3 checks, so run the suite after the merge block and the V12 edit are fixed, before applying it (open items from `H9.2-notes.md`).
- The approach decides on the previous frame's position (movement is applied after input is read), so the swing can start up to one frame after the target enters reach. That is intended and keeps one movement path.
- Marker and swing must stay on the same pick. Both go through the targeting service with the same shape; one check pins it (H9.4.0).
- A weapon swap during an approach is only possible when the weapon controller allows it (it refuses during a swing or charge); the approach re-reads the attack every frame, so either order is safe.
