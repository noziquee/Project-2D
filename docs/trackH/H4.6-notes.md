# H4.6: seed every random source, isolate global state

Written Oct 27, 2026. Not run: no Godot in the sandbox. Expected `SUMMARY passes=1192 failures=0` (1190 + H4-28 and H4-29).

## What I found first

- Only two random sources exist in the game code: the crit roll (`CombatResolver2D._rng`, a static) and each enemy's weighted attack choice (`EnemyAIController2D.rng`, one per enemy, randomly seeded). There is no global `randf()` or `randi()`, and no clock reads, anywhere in the game or the tests.
- No shipped resource has a crit chance above 0, and every test uses a crit chance of 0 or 1 (those never roll) except CCC5, which seeds first. The two tests that use the goblin's real two-way choice (V and CC) seed their own enemy. So the suite was already deterministic in practice; nothing guaranteed it.
- The one real leak: the crit generator is a static, so it kept its position from one part to the next.

## What changed (only `tests/smoke_checks.gd` and `tools/run_checks.sh`; no game code)

- `TEST_SEED` (20261027) and `reset_global_state()`: before every part it re-seeds the crit generator, puts the clip-return mode back, and releases every input action. A part now starts from the same state alone or inside the full run.
- A `node_added` hook seeds every `EnemyAIController2D` with `TEST_SEED` the moment it enters the tree, whichever way the enemy was made (arena, `parked_goblin`, loaded scene). V and CC set their own seed afterwards, as before.
- New part `h4_determinism` with two checks: H4-28 (the crit stream restarts, 24 rolls repeat with both outcomes) and H4-29 (every AI controller in an arena, including one added later, starts at the test seed).
- `tools/run_checks.sh --twice` runs the suite two times and compares every `CHECK` and `PART` line. Identical means the "two runs give identical output" condition of H4.6 holds; if not, it prints the first differing lines and exits 1. I tested the script's logic with a fake `godot` (stable output passes, a changing line fails); the suite itself was not run.

## Things to know

- Seeding changes which of the goblin's two attacks a test sees when nothing seeded it before. Those runs used to differ from run to run and passed, so either pick should pass; if one now fails, that was a hidden dependency, and it will fail the same way every time.
- A rough scan found no test that edits a cached shared `.tres` without `duplicate()`, but the scan is a pattern match, not a proof. A part that fails alone but passes in the full run (H4.5b) is still the real test of isolation.
