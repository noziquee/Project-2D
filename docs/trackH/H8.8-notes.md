# H8.8: touch controls (October 28, 2026)

Status: built and **run headless on Godot 4.7: `SUMMARY passes=1412 failures=0`** (full suite). Not yet tried on a phone: the drag threshold, the button sizes and the hold timing need your thumbs. 22 new checks, H8-118 to H8-139, in part `h8_touch`.

## What you get
- **No aim stick** (D13). `MobileControls.get_aim_stick()` is gone.
- **Right side:** one large attack button (150 px) in the corner, the dodge and skills 1 to 3 in an arc round it, a small weapon-swap button beside the dodge. The heavy button is gone: heavy is a hold on the attack button (D15). Positions are computed from `ARC` in `MobileControls.gd` and the cluster is pinned to the corner by anchors.
- **Attack button:** tap = light attack (assisted). Hold = charge. Hold and drag = aim the heavy attack by hand; the lift releases it that way. A drag presses the existing `aim_*` actions, so `player.gd` reads it like a controller stick.
- **Aimed skills** (Lunge today): nothing happens while the finger is down; the lift casts. Tap = assisted cast, drag = manual aim.
- **Buffs and self skills** (Spin, Empower): cast the moment the finger lands, no drag, no aim (D16). The button asks `player.slot_has_aim_shape(slot)` at touch-down, so a weapon swap that changes the skills changes the buttons' behaviour too.
- **Drag rules:** the finger must move 28 px from where it landed (`drag_threshold`) and leave a dead zone round the button's centre (`aim_dead_zone` 25% of the aim reach) before it aims. Back inside the dead zone drops the manual aim, so the action falls back to assist (a cancel of sorts).
- **After the lift** the aim stays pressed 3 physics frames so the player still reads it when it releases or casts; then it is let go. Hiding the overlay mid-drag lets go at once.

## Things I found in the snapshot you sent (not caused by H8.8)
Your zip had never been run (STATUS says "written, not yet run"). Running it on Godot 4.7 showed:
1. **`tests/h8_aim_checks.gd` did not compile** (lines 63 and 74, `:=` on an untyped value), so the *whole* smoke suite failed to load. Fixed with explicit types.
2. **Real bug, fixed in `player.gd`:** if `attack_light` was pressed and released inside one physics frame, `_light_held` stayed on with nobody holding the button, and the weapon charged until the next press (this made the swap button refuse in H7-65). A finger cannot do this, but a frame hitch on a phone can. Now it counts as a tap.
3. **Real edge, fixed:** the 360 degree fan missed the point straight behind (H8-11).
4. **Test fixtures, not game bugs:** H8-110, 111, 113, 115, 116 assumed `last_aim_direction` was still "right" after earlier checks had legitimately changed it; H7-72 counted Lunge (a dash skill) as a dash press; EEE76 built a SELF skill from an aimed template, which H8.6 correctly rejects; H7-23 clicked a skill while Lunge was still dashing; the targeting check freed its service and then called it. Each is a one-line fixture change.

## One behaviour change worth knowing
An aimed skill now casts when the finger **lifts**, not when it lands (so a drag can aim it first). A tap is a little later than before; that is how mobile MOBAs feel too. Buffs and self skills are unchanged.

## Play-test on a phone
1. Tap the attack button a few times: light attacks, no accidental charge. `charge_start_time` is 0.1 s on the player; a slow tap can start a charge. If it does, raise it to about 0.2.
2. Hold and slide: the weapon should follow the thumb; release swings the heavy attack that way.
3. Lunge: tap (assisted), then drag and lift (manual). Spin and Empower: instant.
4. Check the drag threshold (28 px) and button sizes with a real thumb; they are exports.
