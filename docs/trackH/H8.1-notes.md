# H8.1: audit for assisted aiming (read-only, October 28, 2026)

Status: **audit only. No game code changed.** Answers the questions in `H8-aim-assist-plan.md` step H8.1.
Open questions taken as proposed (you said "Start"): one project-wide light-attack arc, highlight enemies inside the aim shape, remove the aim stick at H8.8.

## 1. How targets can be found today

- `BasicEnemy2D.tscn` and `player.tscn` are already in the group `damageable` (plus `enemy` / `player`). Nothing reads `damageable` yet.
- `Hurtbox2D` (crates, dummies) joins **no** group on purpose: hit rules only call `apply_hit`. For assist it must opt in. That matches the PDF ("only objects explicitly registered as damageable"). Proposal: `Hurtbox2D` gets an export `targetable` (default false) that adds it to `damageable` in `_ready`.
- Eligibility needs: alive (`is_alive()` exists on `Character2D` and `Hurtbox2D`), not the caster's own team (`team` export on both; empty = neutral, never skipped), distance to the shape's range.
- Physics layers (1 player, 2 enemy, 3 world) are for hits, not discovery. Targeting should use the group plus `team`, not a physics query. No line-of-sight rule is proposed.
- Enemy AI aims itself (`EnemyAIController2D.get_aim_direction()`); it does not read the player's path and is unaffected.

## 2. Where aim is read

| Reader | What it does | Consequence for assist |
|---|---|---|
| `Character2D._update_facing_direction()` | calls `_get_aim_direction()` **every physics frame** for facing and weapon pivot | Target search must **not** run inside `_get_aim_direction()`: it would re-pick every frame and break stability. Assist is decided at activation and cached. |
| `Character2D._get_attack_direction()` | returns `_get_aim_direction()`; passed to `try_start_attack`, `begin_charge` | Light tap and heavy begin both take a direction here: one hook point. |
| `AttackComponent2D.begin_charge / release_charge / update_charge_direction` | charge keeps a live direction; release defaults to the one the charge began with | Drag while holding can call `update_charge_direction`; release direction is decided at release. Already supports "aim changes during charge". |
| `AttackComponent2D._resolve_attack_direction()` | fallback chain: given -> `context.aim_direction` -> facing -> right | The no-target chain exists; `last_aim_direction` slots in before `context.aim_direction`. |
| `SkillComponent2D.try_use_slot / try_use_skill` -> `_resolve_direction()` | same chain; `Targeting.SELF` returns zero | Buff skills (SELF) already ignore direction: they need no aim shape. |
| `player.gd::_get_aim_direction()` | stick -> last stick -> mouse (last mouse over HUD) -> facing | Keep for mouse/controller; assist wraps it. |

**`context.aim_direction` is not a "last valid aim".** `FacingComponent2D` rewrites it every frame (attack direction while attacking, else `idle_aim`). A separate persistent field is needed (proposed on `CharacterContext2D`: `last_aim_direction`).

## 3. Input flow (touch relevant)

- `attack_light` already does tap versus hold: a tap is the light attack on **release**; holding past `charge_start_time` begins the heavy charge (`player.gd::_sample_attack_input`). `attack_heavy` is a separate action (controller button 10) that charges immediately.
- So the touch attack button maps to `attack_light`: tap = light, hold = heavy charge. This already matches D14/D15. The new part is only the drag while held.
- Light assist decision point: the release frame (when `_pending_light` is set). Heavy: `begin_charge` (initial) and `release_charge` (final).
- `emulate_mouse_from_touch` is off (H7.6), so touches do not also click `attack_light` (bound to mouse button 1). Unchanged.

## 4. Skills data

- `SkillDefinition2D`: `Behavior { PROJECTILE, AREA, DASH, BUFF, NONE }`, `Targeting { AIM_DIRECTION, SELF }`, plus `max_range`, `area_radius`, `projectile_count`, `spread_degrees`.
- Proposed `aim_shape` rule: empty for BUFF/NONE and SELF skills; PROJECTILE gets Line/Arrow (Fan if it fires a spread); AREA gets a Fan or CircleSelf; DASH gets Line.
- **Duplication risk (section 6 of the roadmap):** `max_range` / `area_radius` already exist. The shape's range must not become a second source of truth. Proposal: the shape owns the **assist** range and indicator size; validation warns when it differs a lot from the skill's own range.

## 5. Tests

`tests/smoke_checks.gd` is split into parts (`--list`, `--only=`). New work would add a part `h8_aim` with pure-logic checks (shapes, scoring, stability, fallback), same as H7 did. The error gate (`expected_errors.txt`) is unaffected as long as new checks log no errors.

## 6. Proposed hook design (for H8.2 to H8.4)

1. `AimShape2D` resources (pure data and geometry; no nodes).
2. `TargetingService2D` (component on the player): `pick(origin, direction, shape_or_arc, range) -> Target + direction`, with a sticky choice cleared on a new activation.
3. `player.gd` gets a small `_assisted_direction(kind)` used by the three activation points (light release, charge begin/release, skill use). `_get_aim_direction()` stays the cheap per-frame read for facing.
4. Manual drag sets a per-action override that expires when the action ends.

## Findings that change the plan

- Assist must not live inside `_get_aim_direction()` (polled every frame). H8.4 wording updated here: decide at activation, cache for the action.
- `Hurtbox2D` needs an opt-in `targetable` flag; the `damageable` group already exists for characters.
- Heavy-while-dragging needs no new attack API: `update_charge_direction` and `release_charge(direction)` exist.
- `last_aim_direction` is a new field; `context.aim_direction` cannot be reused.
