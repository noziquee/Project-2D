# Phase 12.4 – Status effect framework

Written and run in Godot 4.7.2 (headless, Linux): **20 new checks, all passing** (section DDD, DDD1 to DDD20). Expected total after this step: previous total + 20. Expected total after all of Phase 12 (12.1 to 12.4): previous total + 46.

## Why
Bleed, burn and later buffs need the same machinery: apply, tick, refresh or stack, expire, clear on death. It is built once, as data plus one runtime node, so a new status is a `.tres` file and no script.

## What changed (new folder `Characters/Components/Status/`)
- `StatusEffectDefinition2D.gd` (new resource): `id`, `duration`, `tick_interval` (0 = no ticks), `tick_damage`, `stack_rule` (REFRESH, STACK, IGNORE) and `max_stacks`.
- `StatusController2D.gd` (new node): holds the running statuses (time left, stacks, tick timer), ticks them in `_physics_process`, and ends them on expiry or death. API: `apply_status(definition)`, `has_status(id)`, `get_stacks(id)`, `get_remaining(id)`, `remove_status(id)`, `clear()`; signals `status_applied(id, stacks)` and `status_ended(id)`. It stops processing when nothing is running.
- `BleedStatusDefinition.tres` (new, example data): `bleed`, 3 s, 1 damage a second, stacks up to 3. Not assigned to any attack yet.
- `AttackDefinition2D.gd`: new group **Status** with `status_effects: Array[StatusEffectDefinition2D]`.
- `HitData.gd`: `statuses` and `is_periodic`.
- `Character2D.gd`: optional `status_controller` export (child named `StatusController2D`, initialized with the health component), and `_apply_hit_reaction()` skips periodic hits.
- `tests/smoke_checks.gd`: section DDD plus helpers `make_status` and `status_rig`.

## Rules
- **Applying.** A hit that carries statuses applies them when it **deals damage**: the controller listens to the health component's `damaged` signal. A hit that is ignored (invulnerable, dead) applies nothing, and neither does the killing hit. A character with no `StatusController2D` takes the damage and ignores the statuses.
- **Reapplying (same id).** REFRESH sets the time back to `duration`, the stack count stays 1. STACK adds one stack up to `max_stacks` and sets the time back to `duration`. IGNORE leaves the running status alone.
- **Ticking.** Every `tick_interval` seconds the controller applies a periodic hit of `tick_damage x stacks`. A status of `duration` 1 and `tick_interval` 0.5 ticks at 0.5 s and 1.0 s, then ends.
- **Periodic hits** (`is_periodic`) skip crit and defense in the resolver, and cause no knockback, hit stun or swing interruption. They are still ignored while the target is invulnerable, like any hit. Hit and death presentation hooks (`_on_damaged`) still run for each tick.
- **Death** clears every status once and stops the ticks. Runtime state is only in the controller, never in the `.tres`.
- **Left out on purpose:** stat modifiers (for example a defense buff). The roadmap's "tick damage or modifier" is met by tick damage; the first modifier arrives with the buff skill in 13.3, when it has a use. A tick has no source, so there is no kill credit yet.

## The checks (section DDD)
| Check | What it proves |
|---|---|
| DDD1 to DDD4 | A status starts with no immediate tick, nothing ticks before the first interval, the first tick lands at 0.5 s, a 1 s status ticks twice then expires and the controller stops processing. |
| DDD5, DDD6 | REFRESH restarts the time and keeps one stack; a refreshed status outlives its original end. |
| DDD7, DDD8 | STACK stops at `max_stacks`; a tick does `tick_damage x stacks`. |
| DDD9 | IGNORE refuses a second application and does not reset the time. |
| DDD10, DDD11 | A status that kills is cleared once by the death; a dead target takes no ticks and no new status. |
| DDD12, DDD13 | A tick ignores defense and crit; a periodic hit gives no knockback or stun, an ordinary hit with the same numbers does. |
| DDD14, DDD15 | The shipped bleed definition loads with the right values; the shipped characters have no controller yet. |
| DDD16 to DDD18 | `Character2D` finds and initializes a child `StatusController2D`; an arrow whose definition lists bleed damages the target and starts the status; the bleed then ticks. This is the "a definition applies a status with no new script" proof. |
| DDD19, DDD20 | An ignored hit applies no status; a character with no controller takes the damage and ignores the status. |

## To use it in the editor
Give a character a status controller:
1. Open the character scene (for example `Characters/Enemies/BasicEnemy2D.tscn`).
2. In the Scene dock, right-click the root node and choose **Add Child Node**.
3. Type `StatusController2D`, select it and click **Create**. Keep its name.
4. Save the scene (Ctrl+S). Nothing else needs wiring: the character finds the node by its name. To use another name, select the root node and drag the node into **Components > Status Controller** in the Inspector.

Make an attack apply bleed:
1. In the FileSystem dock open an attack `.tres` (for example `Characters/Components/Combat/PlayerHeavyAttackDefinition.tres`).
2. In the Inspector open the **Status** group and click **Status Effects**, then **Add Element**.
3. Click the empty slot, choose **Quick Load**, and pick `Characters/Components/Status/BleedStatusDefinition.tres`.
4. Save (Ctrl+S).

Make a new status: in the FileSystem dock right-click `Characters/Components/Status/`, **Create New > Resource**, choose `StatusEffectDefinition2D`, and fill in the Inspector.
