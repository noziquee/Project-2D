# Phase 13.4 - Input, HUD and the first playable skills: plan in 8 segments

Written October 25, 2026 from the code in the archive (13.3.4) and the `game-components-addon` reference (`cooldown_system`, `ability_system`). **No code was written and nothing was run in Godot.** This replaces the old 13.4 (input and HUD) and 13.5 (first real skills) in the roadmap: they are one phase now, because a HUD with empty slots cannot be play-tested.

Same rules as Phase 9: each segment is small, leaves the game playable, ends with a smoke-test run and a zip of only the changed and new files, and is done only when its `SUMMARY` line matches the number in its notes. The expected number of each segment is fixed in that segment's notes when it is written, counted from the last run you confirm.

## Gate before 13.4.1
13.3.2, 13.3.3 and 13.3.4 are written but never run (expected 791, 804, 815). Run the smoke test once and give me the SUMMARY line. If it is not 815 / 0, we fix that first; everything below is counted from the confirmed total.

## What we take from the addon, and what we do not
| Take (as an idea, rebuilt as scenes) | Leave out |
|---|---|
| Radial "clock hand" wipe over a dimmed icon while cooling down | The addon's `Cooldowns` node and `AbilityCaster`: `SkillComponent2D` already owns cooldowns, gating, cost and refunds. Two sources of truth would drift |
| Seconds counter ("3.2" under 10 s, then whole seconds) | Charges (no skill has them) |
| Ready flash and a small scale pop when the cooldown ends | The code-built `*Style` classes: colours, fonts and panels stay `.tres` files under `UI/HUD/Styles` |
| "Not yet" shake when pressed on cooldown | Key handling inside the UI: input goes through the Input Map and `player.gd` |
| Dim when off cooldown but unaffordable; cost badge; hotkey label | |
| Cast progress shown on the slot | |

## Decisions made for this phase (change any before the segment that needs it)
| Decision | Chosen | Needed by |
|---|---|---|
| Skill keys | Input actions `skill_1`, `skill_2`, `skill_3` on keys 1, 2, 3 (Q stays `weapon_next`). Slot index = action number - 1 | 13.4.2 |
| Radial cooldown wipe | A `TextureProgressBar` in radial fill mode with a plain white square texture, tinted dark. No drawing code. Fallback if it looks wrong: a small `RadialWipe2D` scene with a `_draw()` | 13.4.5 |
| Icons | Skills already have an `icon`. Placeholder SVG icons are made in 13.4.3 and 13.4.7 and replaced when you have art | 13.4.3 |
| Who is told about weapon switches | The bar listens to a `skills_changed` signal on `SkillComponent2D` (added in 13.4.1), not to `WeaponController2D` | 13.4.1 |
| Cooldown display data | `SkillComponent2D` gets `cooldown_started`, `cooldown_finished`, `skill_refused` and `skills_changed` signals plus `get_cooldown_duration()`. The HUD never polls the dictionary for events, it only reads remaining time for the wipe | 13.4.1 |
| Multi-shot | New `projectile_count` (default 1) and `spread_degrees` (default 0) on `SkillDefinition2D`; defaults keep every existing skill unchanged | 13.4.7 |
| Cooldown on weapon switch | Unchanged from 13.0: cooldowns keep running, so a skill used with the sword is still cooling when you switch back | - |

## The segments

### 13.4.1 Skill signals and HUD read API (code only, no scenes)
- **Do:** In `SkillComponent2D` add `cooldown_started(skill, duration)`, `cooldown_finished(skill_id)` (the id, because a cooldown outlives a weapon switch; also emitted when a cancelled cast clears the cooldown), `skill_refused(skill, reason)` (from `try_use_skill()` when `can_use()` returns a reason) and `skills_changed` (from `set_skills()`). Add `get_cooldown_duration(skill_id)` and `get_cast_progress()` (0 to 1 of the running cast). Nothing else changes.
- **Tests:** each signal fires once at the right moment; a cancelled cast emits `cooldown_finished` and `skill_cancelled`; a refusal emits `skill_refused` with the same reason `can_use()` gives; weapon switch emits `skills_changed`; every earlier check still passes.
- **Status:** written Oct 25, not yet run; see `13.4.1-notes.md` (checks FFF1 to FFF10, expected 825 / 0).
- **Done when:** the SUMMARY matches the notes. No visible change in the game.

### 13.4.2 Player gets the skill components, and skill input
- **Do:** Add `ManaComponent2D`, `SkillComponent2D` and `StatusController2D` as children of the player in `player.tscn` (exact names, see the 12.4, 13.2 and 13.3.4 notes). Add `skill_1` to `skill_3` to `project.godot` (copy the event format of `weapon_next`). In `player.gd` read them next to the `weapon_next` check and call `skill_component.try_use_slot(slot, aim_direction)`. A refused press only logs at debug level. Both text edits are the risky part (see V1), so this segment changes nothing else.
- **Tests:** the three nodes exist and initialize; a simulated `skill_1` press calls the slot; a dead player ignores it; the weapon keys and attack input still work.
- **Done when:** the project opens with no new errors and the SUMMARY matches. Still no skills equipped, so pressing 1 to 3 does nothing yet.
- **Status:** written Oct 25, not yet run; see `13.4.2-notes.md` (checks GGG1 to GGG11 plus GGG9pre, expected 837 / 0). It edits three files as text (`player.tscn`, `project.godot`, `player.gd`), not one, because the three belong together.

### 13.4.3 Skills on the sword and the bow (existing definitions only)
- **Do:** Put the four shipped skills on the weapons as data: sword: Lunge (slot 0), Ground Slam (slot 1), Empowerment (slot 2); bow: Power Shot (slot 0), Empowerment (slot 2). Add a placeholder icon to each skill (simple SVGs in `UI/HUD/Icons/`). Check each skill's `weapon_animation` against the clips in `Sword.tscn` and `Bow.tscn`; where a skill names a clip that does not exist, reuse an existing clip for now and log it in the notes (new clips are edited in the editor, not as text).
- **Tests:** both weapons pass `validate_equip()`; equipping each gives the right skills in the right slots; Empowerment keeps cooling across a weapon switch; the player pays mana from its pool.
- **Done when:** you can play with keys 1 to 3, with no HUD yet. Mana regenerates at 5 per second from 100, so Ground Slam (15) and Power Shot (20) are usable about every few seconds; tune the numbers after you play.
- **Status:** written Oct 25, not yet run; see `13.4.3-notes.md` (checks HHH1 to HHH9, expected 846 / 0). The placeholder icons are `GradientTexture2D` resources in `UI/HUD/Icons/`, not SVGs: a new SVG needs an editor import before it loads, and a missing import would break the weapons in a plain smoke-test run.

### 13.4.4 Mana bar scene
- **Do:** `UI/HUD/ManaBar.tscn` and `ManaBar.gd`, built like `HealthBar.tscn`: same card, `.tres` styles for the fill (a blue variant of `bar_fill.tres`), a smoothed counter, and an `AnimationPlayer` with `intro`, `spend` and `restore` clips. It observes `ManaComponent2D.mana_changed` through an exported `mana_source` path. Place it under `HUD` in `Main.tscn` below the health bar.
- **Tests:** binds to a mana pool; spending lowers the shown value and plays `spend`; regeneration raises it; a missing source warns and does not crash.
- **Done when:** the bar moves as you cast.

### 13.4.5 One skill slot scene
- **Do:** `UI/HUD/SkillSlot.tscn` and `SkillSlot.gd`: a card with the icon, the radial `TextureProgressBar` wipe, a seconds label, a hotkey label, a cost label and an `AnimationPlayer` with `ready` (flash and pop), `denied` (shake), `started` (press pop) and `unaffordable` (dim). `bind(skill_component, skill, hotkey_text)`; an empty slot shows the frame only. Cast progress uses the same wipe in a different tint while casting. Dimming uses `can_use()`.
- **Tests:** an empty slot is valid; the wipe follows the remaining cooldown; the counter shows one decimal under 10 s and whole seconds above; `ready` plays when the cooldown ends; `denied` plays on `skill_refused`; a skill with no cost hides the cost label.
- **Done when:** one slot works when placed on its own in a test scene.

### 13.4.6 Skill bar scene and weapon switching
- **Do:** `UI/HUD/SkillBar.tscn`: three `SkillSlot` instances in a row, an exported path to the player's `SkillComponent2D` and `ManaComponent2D`, rebuilt on `skills_changed`, bottom centre of the HUD in `Main.tscn`. Hotkey texts come from the Input Map events of `skill_1` to `skill_3`, so a rebind shows.
- **Tests:** slots follow the equipped weapon; a switch keeps running cooldowns on the right slot; an empty weapon slot shows the empty frame; the bar survives the player dying.
- **Done when:** you can see sword and bow skills swap with Q and the wipes keep running.

### 13.4.7 The new first skills: sword spin and bow multi-shot
- **Do:** (a) `projectile_count` and `spread_degrees` on `SkillDefinition2D`, used in `_execute_projectile()` (one effect per arrow, evenly fanned around the aim; defaults give today's single shot), with validation. (b) `MultiShotSkillDefinition.tres` for the bow's slot 1. (c) `SpinSkillDefinition.tres` for the sword: an area skill centred on the caster; if `AreaEffect2D` cannot be centred on the caster as it is, that is a small separate change, noted first. (d) a "dash slash" variant of Lunge with an `attack` (13.3.3 already supports it) if the plain Lunge feels like movement only. Each skill is one `.tres` plus an entry in the weapon's list; icons are placeholder SVGs.
- **Tests:** three arrows with a spread leave at the right angles and each hits once; count 1 equals the old behavior; spin hits enemies around the caster and not the caster; one check per new `.tres` (loads and validates).
- **Done when:** the sword has Lunge, Spin and Empowerment, the bow has Power Shot, Multi-shot and Empowerment, and the bar shows them.

### 13.4.8 Wrap-up and play-test
- **Do:** README (controls, baseline number), `IMPLEMENTATION_NOTES.md` (skill input, HUD, new signals), the roadmap status table, and a short play-test checklist like V3: cooldown wipe and counter, ready flash, denied shake, mana bar while casting, weapon switch mid-cooldown, dying with skills cooling, cast skills interrupted by a hit, and the unaffordable dim.
- **Done when:** the final SUMMARY is written into the README and roadmap, and your play-test notes are logged as bugs or passes.

## Out of scope for 13.4
Charges, a global cooldown, drag-and-drop skill rearranging, per-skill tooltips, sound and VFX for skills (Phase 15), the channel skill 13.3.5 (still "only if a weapon needs it"), and the passives of Phase 14.

## Risks to watch
- `player.tscn`, `Main.tscn` and `project.godot` are edited as text again (13.4.2, 13.4.4, 13.4.6). V1 showed that is where load errors come from, so each of those segments touches one file and says exactly what changed.
- Nothing here can be run in this workspace. Segments written without a Godot run carry an "expected, not confirmed" number, as in 13.3.2 to 13.3.4. Please run the smoke test after each segment so the counts do not stack up unconfirmed.
- Wipe look: a `TextureProgressBar` wedge may not match the addon's exact look. That is why the fallback is named in the decisions table.
